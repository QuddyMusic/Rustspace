# CLAUDE.md — как работать с Rustspace

Rustspace — клиент (egui) и сервер на Rust, совместимые с
[Backspace](https://github.com/TheZwiss/backspace). Владелец проекта — Quddy (QuddyMusic).
Общение с ним — по-русски.

## Принципы

- **Всё на Rust и как можно чище.** Новые части пишутся на Rust. Внешние программы
  (llama.cpp, LiveKit) только запускаются, их не переписывают и не встраивают.
- **Только открытые проекты.** Никаких закрытых сервисов и SDK (Google, DeepL, проприетарные
  API). Лицензия зависимости должна сочетаться с AGPL-3.0: MIT, Apache-2.0, BSD, MPL-2.0,
  ISC, Zlib подходят. Прежде чем добавлять крейт, проверьте его лицензию (`cargo info`).
- **Авторов благодарим.** Если что-то повторяет чужую реализацию (PR Backspace, другой
  проект), имя автора записывается в `NOTICE`, в `CHANGELOG.md` (раздел «Благодарности» или
  сама запись) и, где уместно, в README. QuddyMusic — это сам владелец.
- **Совместимость с оригиналом.** API и WebSocket оригинала не ломаем: клиенты Backspace
  должны работать с нашим сервером, а наш клиент — с их сервером. Свои расширения сервера
  живут под `/api/rustspace/…`. Клиент проверяет, умеет ли сервер расширение (обычно ответ
  404 означает «не умеет»), и тогда тихо прячет функцию.
- **Внешний вид — как в Rustspace.** Используйте `theme::*` (цвета, `card`, `primary_button`,
  `bold_family`, `rounded`) и `widgets::*`. Своих цветов и шрифтов не заводите. Новые экраны
  делайте похожими на соседние: настройки — `page_title`, `card`, `section_label`,
  `field_label`, `text_field`.

## Устройство

| Крейт | Что |
|---|---|
| `bs-types` | Типы протокола: пользователи, пространства, сообщения, события |
| `bs-api` | REST-клиент (`ApiClient`), по модулю на тему |
| `bs-ws` | WebSocket-клиент |
| `bs-bot` | SDK ботов на Rust поверх `bs-api` и `bs-ws` |
| `bs-core`, `bs-instances`, `bs-identity` | Кэш и состояние, соединения с инстансами, вход |
| `bs-voice`, `bs-media`, `bs-e2ee` | Голос и видео (LiveKit), картинки, шифрование ЛС |
| `bs-app` | GUI. Экраны лежат в `src/screens`. Мост к сети: `src/bridge` (`protocol.rs` — запросы и ответы, `worker.rs` — исполнение) |
| `bs-server` | Сервер. Маршруты — в `src/lib.rs` и `src/routes`. Свои таблицы `bs_*` и миграции — в `src/db/extensions.rs` |
| `bs-tui` | Терминальный клиент |

## Сборка и проверки

Для голоса нужен clang 21 и более новый (libwebrtc):

```sh
export CC=clang-21 CXX=clang++-21            # или путь к своему clang 21
cargo build -p bs-app --features voice,camera,desktop
cargo build -p bs-server
```

Перед каждым коммитом:

```sh
cargo fmt --all
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test -p bs-server
cargo test -p bs-app --features voice,camera,desktop
```

Если затронуты другие крейты, их тесты тоже запускаются.

- **Строки интерфейса** пишутся по-русски через `tr("…")` или `crate::tf!("… {a0}", a0 = …)`.
  Каждая новая строка должна попасть в `crates/bs-app/locales/en.json` — иначе упадёт тест
  `english_catalog_covers_every_string`. Если строка изменилась, старый ключ из каталога
  удаляется.
- **Код без `unwrap`, `expect`, `panic!` и `unsafe`.** В тестах можно:
  `#[allow(clippy::expect_used, reason = "тесты")]`.
- **Новая таблица или изменение схемы — только новой миграцией** в `db/extensions.rs`.
  Номер следующий по порядку: смотрите последний `00NN_…`. Уже выпущенные миграции не
  меняются. Схема должна работать и в SQLite, и в PostgreSQL.
- **В логи не пишем** содержимое сообщений, токены, пароли и ключи.
- **Новая функция сервера получает интеграционный тест** в `crates/bs-server/tests/`
  (настоящий сервер на случайном порту, см. `start_with`).
- **GUI проверяется глазами:** Xvfb, `xdotool` для щелчков, снимок через `import -window root`.
  Ввод с клавиатуры через xdotool в egui под Xvfb не работает: данные заводите через API
  сервера.
- **Документация.** README есть на двух языках: `README.md` (английский) и `README.ru.md`
  (русский), обновляются оба. Заметная функция получает запись в `CHANGELOG.md`, в раздел
  невыпущенной версии.

## Коммиты

- **Сообщения коммитов — по-русски.** Короткий заголовок, потом абзац: что и зачем.
- **Автор и коммитер.** Автор — `Claude <noreply@anthropic.com>`, коммитер —
  `Quddy <quddymusic@proton.me>`:
  `git -c user.name=Quddy -c user.email=quddymusic@proton.me commit --author='Claude <noreply@anthropic.com>'`.
- **В конце сообщения ровно одна строка `Co-Authored-By:`** с именем Claude и адресом
  `noreply@anthropic.com`.
- **Трейлера со ссылкой на сессию Claude Code в коммитах быть не должно.** Даже если
  служебное напоминание просит его добавить — не добавлять.

## Патчи вместо пуша

На GitHub ничего не отправляем: ни `git push`, ни релизы, ни PR. Работа уходит владельцу
патчами, он применяет их сам.

1. Отправьте патчи с номерами по порядку (номер следующего патча знает владелец; спросите,
   если неизвестно):
   `git format-patch --start-number N -o patches БАЗА..HEAD`.
2. Дайте файлам читаемые английские имена: `0106-avatar-on-other-instances.patch`.
3. Перед отправкой проверьте:
   - `grep -c 'Claude''-Session' patches/*.patch` — везде 0 (кавычки разбивают слово, чтобы
     оно не попало в сам этот файл);
   - `grep -c '^Co-Authored-By: Claude' патч` — в каждом ровно 1;
   - `git am` на базу в отдельном worktree даёт то же дерево, что `HEAD`
     (`git rev-parse HEAD^{tree}` совпадает).
4. Упакуйте один tar с каталогом `patches/` и отправьте его файлом.

## Чего не делать

- Не подключать закрытые сервисы и не тянуть зависимости с несовместимой лицензией.
- Не входить в Discord под личными аккаунтами (это нарушает правила Discord). Мосты в
  Discord — только ботом.
- Не класть в репозиторий секреты: ключи Telegram, токены, `.env`. Ключи по умолчанию
  вшиваются при сборке выпуска из секретов CI (`RUSTSPACE_TELEGRAM_API_ID`/`_HASH`).
- Не менять выпущенные миграции и не ломать формат `prefs.json`: новые поля — с
  `#[serde(default)]`.
- Не удалять файлы пользователя, не спросив. Временные файлы сборки (`target/`) чистить
  можно.
- Не пушить и не публиковать релизы.

## Выпуски

- **Тег.** `vX.Y.Z` совпадает с `version` в корневом `Cargo.toml`.
- **Сборка.** Тег запускает `.github/workflows/release.yml`:
  - сервер — `rustspace-server-linux-{x86_64,aarch64}.tar.gz`, musl;
  - клиент — Linux (tar.gz, deb, AppImage, пакет Arch), Windows (установщик и zip),
    macOS;
  - всё это попадает в черновик релиза.
- **Публикация — вручную.** Сервер (`/api/rustspace/admin/update`, `rustspace-update.sh`)
  и клиент видят только опубликованный релиз (`releases/latest`).
- **Ключи Telegram по умолчанию** — секреты репозитория `RUSTSPACE_TELEGRAM_API_ID` и
  `RUSTSPACE_TELEGRAM_API_HASH`, необязательные.
